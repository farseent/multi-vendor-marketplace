# DECISIONS.md

Format: Decision · Alternatives · Reason · Verify?

**D1 Modular monolith.** Alt: microservices. Single deployable, shared transactions (orders + stock + coupons), far less ops for a solo portfolio project; module boundaries (service layer only) keep a later split possible.

**D2 Razorpay Route (test mode) as the implemented provider; Stripe Connect documented only.** Alt: Stripe Connect. Stripe's India availability for marketplaces is restricted per its support documentation, so it is a poor default for an India-based demo. Provider hidden behind `PaymentProvider`. **V1-V3 researched on 2026-11-01: see D44-D49 (status: proposed, pending owner approval).** Fallback: `MockLedgerProvider`.

**D3 Order + SubOrder split.** Alt: one order with per-item vendor status. Per-vendor status, refunds, commission and settlement all key off a vendor slice, so it must be a first-class document.

**D4 Separate payment / refund / settlement states.** Alt: one status enum. They progress independently (a paid order can be partially refunded while settlement is pending); one enum would create impossible-state combinations.

**D5 Money as integer paise.** Alt: decimal/float. Eliminates float errors; rate math uses integers and one explicit rounding step.

**D6 Commission model.** Rate resolution: vendor override → category default → platform default (1000 bps = 10%, configurable). Rate snapshotted on the sub-order at checkout, so later changes never alter history.

- Base for vendor-funded discounts (vendor coupons): `base = subtotal - discount`; `commission = roundHalfUp(base × rateBps / 10000)`; `vendorPayout = base - commission`.
- Platform-funded discounts (admin coupons): customer pays `subtotal - discount`, but `base = subtotal`; vendor payout and commission are unaffected; platform net = `commission - discount` (may be negative, by design).
- Discount allocation across items/vendors: proportional to line subtotal using the largest-remainder method so allocated amounts sum exactly to the total. Rounding happens once per sub-order. Gateway fees borne by the platform (assumption).

**D7 Inventory reserved at checkout via atomic conditional decrement, with a 15-minute expiry.** Alt: decrement at payment; optimistic locking with version field; Redis locks. Decrement-at-payment risks overselling after the customer has paid. Redis locks add a second source of truth. Conditional update inside a Mongo transaction is simple and race-free. Cost: unpaid carts can briefly hold stock.

**D8 Idempotent payment confirmation via status-guarded update.** Three confirmation paths converge on one `markOrderPaid` guarded by `status: pending_payment`. Webhook de-dupe is an additional unique-index on event ID, not the only guard.

**D9 Refund commission reversal is proportional.** `commissionReversed = roundHalfUp(refund × commission.amountPaise / customerTotalPaise)`; the final refund that exhausts the sub-order uses the remainder (`commission - alreadyReversed`) so totals reconcile exactly. Vendor payout reduces by `refund - commissionReversed`. Alt: platform keeps commission on refunds (rejected: penalizes vendors unfairly for platform-approved refunds).

**D10 Settlement hold until delivery + 7-day return window.** Alt: immediate payout at capture. Hold protects against refunds after a vendor has been paid. Depends on provider hold support (V2 verified for Razorpay Route, see D45); otherwise MockLedger simulates it.

**D11 Elasticsearch synced via transactional outbox.** Alt: Mongo change streams; dual-write in request path; periodic full reindex. Outbox guarantees at-least-once delivery without losing events if ES is down, and works the same everywhere; external versioning prevents stale overwrites; reindex is the repair tool. Change streams add operational requirements and weaker retry semantics.

**D12 Mongo text-index fallback for search.** Keeps the site functional if ES is down or if free ES hosting is unavailable at deploy time (**verify V4**). ES remains the primary and required component.

**D13 Redis is cache-only, fail-open.** Alt: Redis for carts/sessions/stock. Nothing durable in Redis means Redis loss is only a performance event. Auth rate limiter degrades to in-process rather than disabling.

**D14 Auth: short-lived access JWT + rotating httpOnly refresh cookie.** Alt: JWT in localStorage; server sessions. In-memory access token avoids XSS-readable storage; rotation with reuse detection limits stolen-token impact. Cross-site cookie constraints (**verify V5**); preferred mitigation is same parent domain.

**D15 Vendor ownership enforced in the service layer with 404 on mismatch.** Alt: controller-only checks; 403. Central service enforcement means any caller (route or job) is covered; 404 avoids confirming existence.

**D16 One shop per vendor user; single `role` field.** Simplicity. Alt: multi-role/multi-shop (deferred).

**D17 Background jobs in-process with Mongo lease locks.** Alt: BullMQ on Redis; separate worker service. Redis-based queues would make Redis durable-critical, contradicting D13; extra service adds deploy cost. Revisit if load demands.

**D18 No guest cart, no email verification, no variants, free shipping.** Scope control for a demonstrable MVP; each can be added later without schema breakage (reserved `shippingPaise`).

**D19 Invoices generated on demand with pdfkit; not GST-compliant.** Alt: store PDFs in S3; compliant tax invoicing. Storage not needed for deterministic output; compliance out of scope (**verify V6** before any real use).

**D20 JavaScript (ESM) + Zod, not TypeScript.** Matches current stack; Zod gives runtime validation at boundaries. TypeScript can be adopted later; say if you want it from the start.

**D21 Coupon reservation at checkout, redemption at payment.** Prevents a single-use coupon being used twice concurrently; released on expiry/cancel.

**D22 ESLint pinned to major version 9.** Use ESLint `^9.0.0` (or the exact approved ESLint 9 version) for linting. Alt: upgrade automatically to a newer major version. Keeping ESLint on major version 9 avoids unplanned configuration and tooling changes. Verify the installed version and configuration compatibility.

**D23 Environment loading via Node.js `--env-file`.** Start the backend using Node.js's built-in `--env-file` option to load environment variables from the selected environment file. Alt: load environment files through a separate library such as `dotenv`. This avoids an additional runtime dependency and keeps environment loading at the process startup level. Verify the startup scripts, required `NODE_ENV`, and behavior when environment files are missing.

**D24 Login rate limiting counts every attempt.** Use a custom login limiter that counts every login attempt, not only failed attempts. Alt: count only failed attempts or rely on a generic rate limiter. Counting every attempt applies the limit consistently to all login traffic. Verify that successful and failed login attempts both increment the counter.

**D25 Structural role guard in `app.js`.** Enforce role-based access through a structural role guard mounted in `app.js`. Alt: scatter role checks across individual controllers and handlers. Centralized route-level enforcement makes access rules consistent and reduces the risk of accidentally exposing protected routes. Verify that each protected route is mounted behind the appropriate role guard and that public routes remain accessible.

**D26 Refresh returns the session; client refresh is single-flight.** The refresh endpoint returns `{ user, accessToken }`, and the client uses a single-flight mechanism so concurrent requests share one in-progress refresh operation. Alt: return only a new access token and allow each failed request to trigger its own refresh. Returning the session keeps the client’s authentication state synchronized, while single-flight refresh avoids competing refresh requests when refresh-token rotation is enabled. Verify the response contract, concurrent-request behavior, and refresh-token rotation.

**D27 Minimum bcrypt cost is 12.** Enforce a minimum `BCRYPT_COST` of 12, even if a lower value is configured. Alt: accept any configured bcrypt cost. A minimum cost prevents the application from silently using a weaker password-hashing work factor. Verify that values below 12 are rejected or safely raised to 12, and that valid values of 12 or higher work correctly.

**D28 Vendor identity is looked up per request.** Resolve the authenticated vendor's identity from the database on each request rather than relying on potentially stale vendor data embedded in the access token. Alt: trust vendor identity claims from the JWT. This ensures vendor access uses current database state.

**D29 S3 is optional at application boot.** The application must start even when S3 is not configured; image upload operations return HTTP 503 when S3 is unavailable or unconfigured. Alt: fail application startup without S3 configuration. This allows development and deployment without requiring image storage immediately.

**D30 Admin mutations are audited starting in Phase 2.** Record administrative mutation actions in the audit log from Phase 2 onward. Alt: introduce audit logging in a later phase. This provides traceability for administrative changes.

**D31 Stock changes only through the stock endpoint.** Inventory adjustments must go through the dedicated stock endpoint rather than general product update operations. Alt: allow stock quantities to be modified through product CRUD. This keeps inventory changes controlled and prevents accidental stock modifications.

**D32 Shop logos share the `products/{vendorId}/` S3 prefix.** Store shop logo objects under the same vendor-specific S3 prefix used for product images. Alt: use a separate prefix for shop logos. This simplifies vendor-scoped object storage and ownership checks.

**D33 Product and shop writes run in transactions with the outbox entry.** Every product and shop write that affects search visibility must run in a MongoDB transaction together with its corresponding `searchOutbox` entry. Alt: plain MongoDB saves followed by separate outbox writes. Transactions prevent product/shop changes from being committed without their corresponding search-sync event. MongoDB must run as a replica set (already required).

**D34 The sync job re-reads current state; the outbox entry only means "look at this product again".** The search sync job re-reads the current product and vendor/shop state before deciding whether to index or delete the document. The `op` field in the outbox is advisory and stored for humans. Alt: blindly execute the operation recorded in the outbox. Re-reading current state makes replays idempotent and prevents stale outbox operations from overwriting newer state.

**D35 Index version = max(product.updatedAt, shop.updatedAt) in milliseconds, with `version_type=external_gte`.** Deletes carry a version too. Alt: use only `product.updatedAt` with `version_type=external`. A product's search visibility depends on its shop, so shop changes must also advance the index version. This ensures that re-approving a shop can outrank a delete written while it was suspended.

**D36 An Elasticsearch outage does not consume an entry's attempts.** A failed bulk request pauses the whole sync job with growing back-off (2 seconds up to 60 seconds). Only per-document rejections increment entry `attempts`, with back-off up to 5 minutes. At 10 attempts, the entry is logged at `error`, kept, and no longer claimed. A successful reindex deletes flagged entries older than itself. Alt: count every failed bulk request as an entry attempt. Separating infrastructure failures from document-level failures prevents healthy entries from being incorrectly exhausted during an Elasticsearch outage.

**D37 Fixed name `products_v0` for the first index.** Use `products_v0` as the concrete index name during the first index creation. Subsequent reindexes use timestamp-based names. Alt: generate a timestamp-based name for every initial boot. A fixed first-index name prevents concurrent first boots from creating multiple indices and attaching different indices to the alias.

**D38 Cache circuit breaker.** After a Redis failure, cache reads and writes are skipped for 5 seconds. Deletes are always attempted. Alt: continue attempting every Redis operation after a failure. Skipping reads and writes temporarily reduces repeated failures and unnecessary latency while ensuring cache invalidation is still attempted.

**D39 The cart stores only product ids and quantities; every read prices it from Mongo.** Alt: store prices in the cart; read the cache or the search index. Stored prices go stale and the cache/index may lag, so the preview always reads current price, status and stock from Mongo. Lines whose product is not `active`, or whose shop is not `approved`, are returned as `status: unavailable` and are excluded from totals; lines asking for more than the current stock are returned as `insufficient_stock` (with `available`), still priced, and set `hasIssues`. The exact stock number is only exposed on an `insufficient_stock` line.

**D40 Adding to the cart is strict, the preview is only a warning.** `PUT /cart/items/:productId` answers 409 `CONFLICT` for any product that cannot be bought (draft, archived, suspended, unapproved shop, or a non-existent id, all identical so ids cannot be probed), 409 `OUT_OF_STOCK` (`details: [{productId, available}]`) when quantity exceeds current stock, 422 for quantity outside 0-10, and 409 `CONFLICT` for a 31st distinct product. Stock can still drop later, which is why the preview warns and checkout (Phase 5) re-checks atomically. Cart writes are single atomic updates (positional `$set`, or an upsert guarded by "product absent and cart not full") so parallel requests cannot lose or duplicate lines.

**D41 Coupon rules are one pure function (`coupons.rules.js: evaluateCoupon`).** No database, no clock of its own, so the same code is table-tested now and reused at checkout. Check order: `disabled`, `not_started`, `expired`, `wrong_vendor`, `below_min_order`, `total_limit_reached`, `user_limit_reached`; the service adds `not_found`, and the cart adds `empty_cart`. A vendor coupon covers only that vendor's lines; a platform coupon covers all. `minOrderPaise` is measured on the covered lines. Percent discount = `roundHalfUp(coveredSubtotal x value / 100)`, capped by `maxDiscountPaise` (percent coupons only), then clamped to the covered subtotal (so a large fixed coupon never goes negative). The discount is allocated to covered lines proportional to line subtotal with the largest-remainder method (D6), so line shares sum exactly to the discount. Per-user usage counts `couponRedemptions` rows in `reserved` or `redeemed`; total usage uses `coupon.usedCount`. Both are only written by checkout (Phase 5).

**D42 Coupon CRUD rules.** `code`, `type`, `scope`, `vendorId`, `fundedBy` and `usedCount` are never editable after creation; scope/funding/vendor are decided by the route (vendor id from the shop record), never the body. Vendor coupon routes require an approved shop (403 `VENDOR_NOT_APPROVED`) and are scoped by `vendorId` (404 for another vendor's coupon, D15). Admin routes see platform coupons only. Admin create/update are audited as `coupon.created` / `coupon.updated` (D30). Edits are validated as the resulting combination (percent 1-90, fixed >= 100 paise, `expiresAt > startsAt`).

**D43 A saved cart coupon is re-evaluated on every cart read.** `POST /cart/coupon` only saves a code that is valid right now (else 422 `COUPON_INVALID`, `details.reason`, and the previous coupon is kept). If a saved coupon later stops being valid (expired, disabled, cart fell below the minimum) the cart still answers 200 with `coupon: null` and `couponError: { code, reason }` and no discount; the user removes it or fixes the cart. Checkout re-validates regardless.

**D46 Webhook handling rules (V3) (Accepted). Owner choice: yes, with atomic conditional claiming.** Verified [S7, India page, read in full]: when a webhook secret is set, each request carries `X-Razorpay-Signature`, computed with HMAC-SHA256 using the webhook secret as key and the **raw** request body as message, as a hex digest; the body must not be parsed or cast first; the secret is distinct from the API key secret; after a secret change, retries of older events are signed with the old secret. `x-razorpay-event-id` is unique per event and is the duplicate key. Ordering is not guaranteed (the documented `payment.authorized` then `payment.captured` order "may not be followed"). Verified [S8, S9]: delivery is at least once; a response slower than 5 seconds counts as a timeout and the event is resent; non-2xx responses are retried with exponential backoff for 24 hours, after which the webhook is disabled and an email is sent; the Dashboard can replay missed events, at most 5 times per 24 hours. Verified [S10]: `payment.failed` is not triggered when a payment fails during first authorisation; the sequence of events inside payment payloads is not fixed; the envelope is `{ entity: "event", account_id, event, contains: [...], payload: { <entity>: { entity: {...} } } }` (from the `payment.authorized` sample). Verified [S11]: `order.paid` carries both the order and the payment entity; `payment.captured` carries only the payment. Verified event names [S10, S11, S12]: `payment.authorized`, `payment.captured`, `payment.failed`, `order.paid`, and for Route `transfer.processed`, `transfer.failed`, `settlement.processed` (Razorpay words its trigger two ways on different pages: settled with the parent merchant, or paid out to your bank account), `product.route.under_review`, `product.route.needs_clarification`, `product.route.activated`. **Secondary source only [X1]:** `refund.created`, `refund.processed`, `refund.failed`; needs check against Razorpay's own refund webhook page at the start of Phase 6. Test-mode webhooks [S7]: localhost does not work; many tunnel services are blacklisted for security, including `ngrok.io`, `loca.lt`, `webhook.site` and `requestbin.com`; Razorpay suggests `zrok` or a staging deployment; a default OTP is documented for setting up test-mode webhooks. **Decision:** (1) `webhookEvents.eventId` stores the `x-razorpay-event-id` header, not a body field. (2) Phase 5 handles `payment.captured`, `payment.failed` and `order.paid`; every other event is stored as `ignored` and answered 200. (3) Event content never decides state alone: payment state comes from a provider fetch (ARCHITECTURE 3.2). (4) Handlers are order-independent and only move status forward, so a late `payment.failed` never undoes a capture. (5) **Duplicate recovery with atomic claiming (our own design, not Razorpay behaviour):** the first delivery inserts the row with status `received` and `claimedAt = now`. On a duplicate key, the handler answers 200 and stops if the row is `processed`, `ignored`, or `received` with `claimedAt` newer than 60 seconds. If the row is `failed`, or `received` with `claimedAt` older than 60 seconds, the handler tries one conditional `findOneAndUpdate` whose filter is exactly that condition and whose update sets status `received`, `claimedAt = now` and increments `attempts`. Because the filter and the update are a single-document operation, MongoDB lets only one concurrent request match; only the request that gets a document back processes the event, every other request answers 200. After processing, the row becomes `processed` or `failed`. `markOrderPaid` stays status-guarded (D8) as a second line of defence against a claim that outlives 60 seconds. This adds one field, `claimedAt`, to `webhookEvents` (applied in DATABASE_SCHEMA.md). (6) The reconcile job (every 5 minutes) covers lost or never-sent events. Alt: process asynchronously after answering 200 (rejected: needs a queue, D17); use only `payment.captured` (rejected: `order.paid` carries the order too and is cheap to accept).

**D47 Two Razorpay transfer limits constrain existing business rules (Accepted). Owner choices: (a) yes; (b) Option 1. D6 is unchanged.** (a) _Minimum transfer of 100 paise_ (see D45 for how well this is verified). A sub-order payout can be below 100 paise (the minimum product price is 100 paise and a 10% commission leaves 90). **Decision:** checkout answers 422 `VALIDATION_ERROR` with `details.reason: "payout_below_minimum"`, in provider-neutral code so MockLedger behaves identically. **D48 `/payments/verify` and capture rules (Accepted).** Verified [S13]: the Checkout callback returns `razorpay_payment_id`, `razorpay_order_id` and `razorpay_signature`; the signature is `hmac_sha256(order_id + "|" + razorpay_payment_id, key_secret)` as a hex digest, and the order id is taken from the server (the standard-checkout page says to retrieve it from your server; the partner-flow page says outright not to use the one returned by Checkout). **D49 Vendor linked accounts in Phase 5 (Accepted). Owner choice: Option A, with validation, audit logging and the payout-account endpoints deferred.** Gap found during research: `payoutAccount.linkedAccountId` exists only as a schema field. No code creates it, `POST/GET /vendor/payout-account` in API_CONTRACTS is unimplemented and no phase scheduled it, yet every Razorpay order transfer needs a linked account [S1]. **Decision:** (1) Linked accounts are created by the owner in the Razorpay Dashboard [S6]. (2) An admin-only script, `npm run link-account -- --vendor <vendorId|shopSlug> --account <acc_id> --admin <email>`, attaches one. It changes nothing and exits non-zero unless all of these hold: the `--admin` email belongs to an existing active user with role `admin`; the vendor exists, is `approved` and its user is `active`; the account id matches `^acc_[A-Za-z0-9]+$`; the payment provider confirms the account (Razorpay provider: the account exists under the merchant and is usable for Route; MockLedger: only the deterministic id for that vendor); the account id is not attached to another vendor; and, if the vendor already has a different active account, `--replace` was passed. **Resolved in 5e [S19]:** the Razorpay adapter calls `GET /v2/accounts/:id` and accepts an account that exists under the merchant (Razorpay answers 400 otherwise), is of type `route` and is not `suspended`. **Not checked (known issue):** whether Route is _activated_ for the account; that is a separate product-configuration resource that needs a product id we do not store, so a not-yet-activated account shows up as a provider error (502) when an order is created. (4) MockLedger derives a deterministic account `acc_mock<vendorId>` (letters and digits only, so it passes the same `acc_` id check) at call time and treats it as active; it stores nothing on the vendor, so no schema change is needed (if you want mock accounts persisted, say so). (5) Checkout rejects a cart containing a vendor without an active payout account with 409 `CONFLICT`, `details.reason: "vendor_payout_unavailable"` and the affected `productIds`, before any write. (6) `POST /vendor/payout-account` and `GET /vendor/payout-account` are marked deferred and unimplemented in API_CONTRACTS. Alt (rejected by the owner): implement those endpoints against Razorpay's account, stakeholder and product-configuration APIs now; run Phase 5 on MockLedger only.

**D51 Platform default commission comes from `PLATFORM_COMMISSION_BPS` (Accepted). **D52 Commission rate for a sub-order with several categories (Proposed, implemented).** D6 says vendor override, then category default, then platform default, and snapshots ONE rate per sub-order, but a sub-order can hold products from several categories. Implemented: the vendor override wins; otherwise a category default applies only if every item's category has the same non-null default (`rateSource: category`); otherwise the platform default (`PLATFORM_COMMISSION_BPS`) applies (`rateSource: platform`). Alt: per-line rates (rejected: the schema stores one rate per sub-order); highest or lowest category rate (rejected: arbitrary). `lib/commission.js`, tested in `phase5a.unit.test.js`.

**D53 Checkout behaviour that API_CONTRACTS did not specify (Proposed, implemented).** (1) `couponCode` omitted = use the coupon saved in the cart, `null` = no coupon, a string = that code (re-validated either way, D43). (2) The first answer is 201; a retry with the same `Idempotency-Key` returns the same order with 200 (a request that lost the race waits up to 4 s for the winner's provider order); a key whose order expired or failed is a 409 telling the client to use a new key. (3) The order number counter is incremented before the transaction, so a rejected checkout can leave a gap in `MP-YYYYMMDD-NNNNNN` (numbers are unique, not gapless). (4) Checkout clears the cart inside the transaction; that write also serialises two checkouts of one customer (the second finds an empty cart), which is what keeps the per-user coupon limit race-free. (5) If creating the provider order fails, the order is expired (stock and coupon restored, D7) AND the customer's cart and saved coupon are put back, so a provider outage does not cost them their cart; ARCHITECTURE 3.1 only required the expiry. (6) The Idempotency-Key must be 8-100 characters of letters, digits and `. _ : -`; 422 otherwise.

**D54 Late capture and refunds, as built (Proposed, implemented).** A payment that is captured after its order expired first tries to re-reserve every line in one transaction (success: the order becomes `placed`, the coupon is honoured even if its limit was reached meanwhile because the customer already paid the discounted price). If any line is gone the transaction rolls back and the customer is refunded in full: one order-level `Refund` (`reason: failed_late_capture`, idempotency key `late_capture:<paymentId>`), the provider is asked once with `reverse_all: 1` (D45), and the order stays `expired` with `paymentStatus: paid, refundStatus: full`. Because Razorpay's `receipt` is only a label and not an idempotency key [S4, read 2026-11-01], the provider call is protected by an atomic claim (`providerCallAt`, 60 s) so racing callers never both refund; a refund the provider refused stays `initiated` and the reconcile job retries it. The refund is order-level: `refunds.subOrderId` and `refunds.requestedBy` are optional for this reason (the schema had them required). The ARCHITECTURE asks for "an audit event"; `auditLogs.actorId` requires a user, so the system event is written to the log (`order.late_capture_refunded`, level info) and the `Refund` row is the durable record. **Known limit:** reconcile asks the provider about an expired order for one hour after expiry (a lost webhook for a later payment is not caught after that).

**D55 Development-only mock payment endpoint (Proposed, implemented).** `POST /payments/mock/complete { orderId }` (customer, owner of the order) returns what Checkout would hand the browser, so the UI can be demonstrated without Razorpay. It answers 404 unless the provider is the MockLedger and `NODE_ENV` is not `production`; the environment check already refuses the mock in production, so this is a second lock.

**D56 Schema and naming differences from DATABASE_SCHEMA (Proposed, implemented; the schema file is updated).** `payments.provider` also allows `mock`; `payments.providerOrderId` is unique but sparse (the row is written in the checkout transaction, the provider order after the commit); `webhookEvents.claimedAt` (D46); `refunds.subOrderId` and `refunds.requestedBy` optional and `refunds.providerCallAt` (D54); new audit action `vendor.payout_account_attached` (D49); the `subOrders` collection name is set explicitly because Mongoose would otherwise create `suborders`. Order status on expiry: the sub-orders of an expired order become `cancelled` (the sub-order enum has no `expired`), and `orders.paymentStatus: failed` is not used in Phase 5 (a failed attempt must not block the customer's next try on the same provider order).
